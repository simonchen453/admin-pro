# review-code

全面审查代码质量，从架构、代码结构、风格、安全、性能等多个维度提供专业的代码评审意见。

## 使用方式

```
/review-code [文件路径或目录]
```

如果不指定路径，将审查当前工作目录下的代码变更。

## 审查维度

### 1. 架构设计
- **分层架构**: 是否遵循清晰的分层结构（Controller/Service/Repository）
- **模块划分**: 模块职责是否单一，边界是否清晰
- **依赖关系**: 是否存在循环依赖，依赖方向是否合理
- **设计模式**: 是否合理使用设计模式，是否过度设计
- **接口设计**: API 接口设计是否符合 RESTful 规范
- **数据库设计**: 表结构是否合理，索引是否优化
- **扩展性**: 代码是否易于扩展，是否符合开闭原则
- **解耦合**: 组件之间耦合度是否合理

### 2. 代码结构
- **职责单一**: 类/方法是否职责单一（SRP）
- **方法长度**: 方法是否过长（建议不超过50行）
- **类大小**: 类是否过大（建议不超过500行）
- **参数数量**: 方法参数是否过多（建议不超过5个）
- **嵌套深度**: 代码嵌套层级是否过深（建议不超过4层）
- **圈复杂度**: 方法逻辑复杂度是否过高
- **代码重复**: 是否存在重复代码（DRY原则）
- **抽象层次**: 同一方法内抽象层次是否一致

### 3. 代码风格
- **命名规范**:
  - 类名：PascalCase，名词
  - 方法名：camelCase，动词开头
  - 变量名：camelCase，语义清晰
  - 常量：UPPER_SNAKE_CASE
  - 布尔值：is/has/can 开头
- **注释质量**:
  - 是否有必要的类/方法注释
  - 注释是否与代码同步
  - 是否避免无意义注释
  - 复杂逻辑是否有解释性注释
- **代码格式**: 缩进、空格、换行是否统一
- **魔法数字**: 是否存在未定义的魔法数字
- **TODO/FIXME**: 是否有遗留的临时代码标记

### 4. 安全性
- **注入攻击**:
  - SQL 注入风险（使用参数化查询）
  - XSS 攻击风险（输出转义）
  - 命令注入风险
  - LDAP/XML 注入
- **身份认证**:
  - 是否有完整的身份认证
  - Token/Session 管理是否安全
  - 密码存储是否加密（bcrypt/PBKDF2）
- **权限控制**:
  - 是否有细粒度权限校验
  - 越权访问风险（水平/垂直越权）
  - 接口是否有访问控制
- **敏感数据**:
  - 密码/密钥是否硬编码
  - 敏感信息是否加密存储
  - 日志是否泄露敏感信息
  - 前端是否暴露敏感数据
- **输入验证**:
  - 参数校验是否完整（@Validated）
  - 文件上传类型/大小是否限制
  - 是否防止 CSRF 攻击
- **依赖安全**:
  - 第三方库是否存在已知漏洞
  - 依赖版本是否过时

### 5. 性能优化
- **数据库性能**:
  - N+1 查询问题
  - 是否使用索引
  - 批量操作是否合理
  - 是否存在全表扫描
  - 是否有慢查询风险
- **缓存策略**:
  - 是否合理使用缓存
  - 缓存失效策略是否正确
  - 是否存在缓存穿透/雪崩风险
- **资源管理**:
  - IO 流是否正确关闭
  - 数据库连接是否释放
  - 大对象是否及时清理
- **并发处理**:
  - 是否有线程安全问题
  - 锁的粒度是否合理
  - 是否存在死锁风险
- **算法效率**:
  - 时间复杂度是否合理
  - 是否有不必要的循环嵌套
  - 集合使用是否合理

### 6. 异常处理
- **异常捕获**:
  - 是否捕获了合适的异常类型
  - 是否避免捕获 Exception/Throwable
  - 是否避免空的 catch 块
- **异常传播**:
  - 异常是否正确向上传递
  - 是否使用自定义业务异常
- **资源清理**:
  - finally 块或 try-with-resources
  - 异常情况下资源是否释放
- **异常日志**:
  - 是否记录完整的异常堆栈
  - 日志级别是否合适

### 7. 日志规范
- **日志级别**: ERROR/WARN/INFO/DEBUG 使用是否恰当
- **日志内容**:
  - 关键业务操作是否有日志
  - 日志信息是否完整（who/what/when）
  - 是否记录必要的上下文信息
- **日志性能**:
  - 是否避免大量 DEBUG 日志
  - 是否使用占位符而非字符串拼接
  - 循环中是否有过多日志

### 8. 测试覆盖
- **单元测试**:
  - 核心业务逻辑是否有单元测试
  - 测试覆盖率是否足够（建议 >70%）
  - 边界条件是否测试
- **测试质量**:
  - 测试是否独立可重复
  - 测试命名是否清晰
  - 是否使用 Mock 隔离依赖
- **集成测试**: 是否有必要的集成测试

### 9. 可维护性
- **可读性**: 代码是否易于理解
- **可扩展性**: 新增功能是否容易
- **可配置性**: 硬编码配置是否提取
- **文档完整性**:
  - API 文档是否完整
  - 复杂逻辑是否有设计文档
  - README 是否更新

### 10. 框架规范 (Spring Boot)
- **注解使用**:
  - @Transactional 使用是否正确
  - @Validated/@Valid 参数校验
  - @Async 异步调用是否合理
  - @Cacheable 缓存注解
- **Bean 管理**:
  - 是否正确使用 @Component/@Service/@Repository
  - 是否存在循环依赖
  - Bean 作用域是否合理
- **配置管理**:
  - 是否使用 @ConfigurationProperties
  - 配置文件是否区分环境
  - 敏感配置是否加密

### 11. 数据库规范
- **事务管理**:
  - 事务边界是否合理
  - 事务隔离级别是否正确
  - 是否避免大事务
- **ORM 使用**:
  - 是否合理使用 JPA/MyBatis
  - 懒加载问题
  - 批量操作优化
- **SQL 质量**:
  - SQL 是否可读
  - 是否避免复杂子查询
  - 是否使用批量操作

### 12. API 设计
- **RESTful 规范**:
  - HTTP 方法使用是否正确（GET/POST/PUT/DELETE）
  - URL 设计是否语义化
  - 状态码使用是否恰当
- **接口版本**: 是否有版本控制
- **响应格式**:
  - 统一的响应格式
  - 错误信息是否友好
  - 分页/排序/过滤是否标准化
- **接口文档**: Swagger/OpenAPI 文档是否完整

## 执行步骤

当用户调用此 skill 时:

1. **确定审查范围**
   - 如果指定了文件/目录，审查该范围
   - 如果未指定，使用 `git diff` 或 `git diff --staged` 获取变更文件
   - 使用 `git status` 查看未提交的文件

2. **读取代码文件**
   - 使用 Read 工具读取相关文件
   - 使用 Grep 搜索特定模式（如 TODO、FIXME、硬编码密码等）
   - 使用 Glob 查找特定类型文件

3. **多维度分析**
   - 按照12个审查维度逐一检查
   - 记录发现的问题和建议
   - 标注问题的严重程度（严重/重要/优化）

4. **生成审查报告**
   - 按照输出格式生成完整报告
   - 给出评分和总体评价
   - 提供可执行的改进建议

5. **关键检查命令**
   ```bash
   # 查找潜在安全问题
   grep -r "password.*=.*\"" .
   grep -r "TODO\|FIXME" .

   # 查找大文件
   find . -name "*.java" -exec wc -l {} \; | sort -rn | head

   # 统计代码行数
   cloc . --exclude-dir=node_modules,target,.git
   ```

## 审查优先级

1. **P0 - 安全问题**: 必须立即修复
2. **P1 - 严重缺陷**: 影响功能或性能的严重问题
3. **P2 - 重要建议**: 影响代码质量和可维护性
4. **P3 - 优化建议**: 锦上添花的改进

## 注意事项

- 保持客观专业，避免主观臆断
- 不仅指出问题，更要给出具体可行的解决方案
- 肯定代码中做得好的地方
- 考虑项目背景和业务场景
- 遵循项目已有的代码规范
- 避免过度设计和过度优化
