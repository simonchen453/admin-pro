# review-mr

审查 GitLab Merge Request 代码，提供专业的代码评审意见。

## 使用方式

```bash
# 审查指定 MR 编号
/review-mr 123

# 审查指定 GitLab URL
/review-mr https://gitlab.com/group/project/-/merge_requests/456

# 审查当前分支的 MR
/review-mr
```

## 前置要求

需要安装并配置 GitLab CLI (glab)：

```bash
# macOS
brew install glab

# Linux
sudo apt install glab
# 或
sudo dnf install glab

# Windows
scoop install glab
# 或
choco install glab

# 配置认证
glab auth login
```

## 审查流程

1. 获取 MR 基本信息（标题、描述、作者、目标分支等）
2. 获取变更文件列表和统计信息
3. 获取代码变更内容（diff）
4. 多维度分析代码质量
5. 生成详细的审查报告

## 审查维度

### 1. 代码质量
- **可读性**: 代码是否清晰易读，逻辑是否清晰
- **命名规范**:
  - 类名：PascalCase，语义明确
  - 方法名：camelCase，动词开头
  - 变量名：camelCase，见名知意
  - 常量：UPPER_SNAKE_CASE
- **代码重复**: 是否存在重复代码（DRY 原则）
- **方法复杂度**: 方法是否过长或过于复杂（建议不超过 50 行）
- **类职责**: 是否符合单一职责原则（SRP）
- **注释质量**: 注释是否必要且与代码同步

### 2. 安全性
- **注入攻击**:
  - SQL 注入风险（检查是否使用参数化查询）
  - XSS 攻击风险（检查输出是否转义）
  - 命令注入风险
- **敏感信息**:
  - 密码、API Key 是否硬编码
  - 配置文件是否包含敏感信息
  - 日志是否泄露敏感数据
- **权限校验**:
  - 接口是否有权限验证
  - 是否存在越权访问风险
  - 数据访问是否有权限控制
- **输入验证**:
  - 参数校验是否完整（@Valid/@Validated）
  - 文件上传是否有类型和大小限制
  - 是否防止 CSRF 攻击
- **依赖安全**: 第三方库是否存在已知漏洞

### 3. 性能问题
- **数据库性能**:
  - N+1 查询问题
  - 是否缺少必要的索引
  - 是否存在全表扫描
  - 批量操作是否合理
  - 事务范围是否过大
- **缓存使用**:
  - 是否合理使用缓存
  - 缓存失效策略是否正确
  - 是否存在缓存穿透/雪崩风险
- **资源管理**:
  - IO 流是否正确关闭（try-with-resources）
  - 数据库连接是否释放
  - 大对象是否及时清理
- **并发处理**:
  - 是否有线程安全问题
  - 共享变量是否有同步保护
  - 是否存在死锁风险
- **算法效率**: 时间复杂度是否合理

### 4. 框架规范 (Spring Boot / Java)
- **注解使用**:
  - @Transactional 事务管理是否正确
  - @Validated/@Valid 参数校验
  - @Cacheable 缓存注解使用
  - @Async 异步调用是否合理
- **异常处理**:
  - 是否正确处理异常
  - 异常信息是否友好
  - 是否使用自定义业务异常
  - 是否避免吞掉异常
- **日志记录**:
  - 日志级别是否恰当（ERROR/WARN/INFO/DEBUG）
  - 关键业务操作是否有日志
  - 是否使用占位符而非字符串拼接
  - 是否记录完整的异常堆栈
- **RESTful 规范**:
  - HTTP 方法使用是否正确（GET/POST/PUT/DELETE/PATCH）
  - URL 设计是否语义化
  - 状态码使用是否恰当
  - 响应格式是否统一

### 5. 架构设计
- **分层架构**: 是否遵循清晰的分层（Controller/Service/Repository）
- **依赖关系**: 是否存在循环依赖
- **设计模式**: 是否合理使用设计模式
- **接口设计**: API 接口设计是否合理
- **扩展性**: 代码是否易于扩展

### 6. 测试覆盖
- **单元测试**: 核心业务逻辑是否有单元测试
- **测试质量**: 测试是否独立可重复
- **边界测试**: 边界条件是否测试
- **异常测试**: 异常场景是否覆盖

### 7. 数据库设计
- **表结构**: 字段类型、长度是否合理
- **索引**: 是否有合适的索引
- **外键**: 关联关系是否正确
- **SQL 质量**: SQL 是否高效、可读

### 8. 可维护性
- **代码组织**: 文件和目录结构是否清晰
- **配置管理**: 硬编码配置是否提取到配置文件
- **文档**: 复杂逻辑是否有文档说明
- **向后兼容**: 修改是否考虑向后兼容性

## 执行步骤

当用户调用此 skill 时:

### 1. 检查 glab 是否已安装
```bash
which glab || echo "请先安装 glab: brew install glab"
glab auth status
```

### 2. 获取 MR 信息

如果用户提供了 MR 编号或 URL:
```bash
# 获取 MR 基本信息（JSON 格式）
glab mr view <MR编号> --json

# 或者获取可读格式
glab mr view <MR编号>
```

如果用户没有提供参数，尝试获取当前分支的 MR:
```bash
# 列出当前分支相关的 MR
glab mr list --source-branch=$(git branch --show-current)

# 或者获取当前分支的 MR
glab mr view
```

### 3. 获取代码变更

```bash
# 获取 MR 的 diff
glab mr diff <MR编号>

# 获取变更文件列表
glab mr view <MR编号> --json | jq '.changes'

# 或使用 git 命令
git diff origin/<target-branch>...origin/<source-branch>
```

### 4. 读取变更文件内容

使用 Read 工具读取每个变更文件的完整内容，结合 diff 进行分析。

### 5. 多维度分析

按照审查维度逐一检查：
- 使用 Grep 搜索潜在问题（如硬编码密码、TODO 等）
- 分析代码结构和逻辑
- 检查安全隐患
- 评估性能影响
- 检查框架使用规范

### 6. 生成审查报告

按照输出格式生成完整的审查报告。

## 常用命令参考

```bash
# 查看 MR 详情
glab mr view 123

# 查看 MR diff
glab mr diff 123

# 列出所有打开的 MR
glab mr list --state=opened

# 列出我创建的 MR
glab mr list --author=@me

# 查看 MR 的讨论
glab mr note list 123

# 批准 MR
glab mr approve 123

# 在 MR 上添加评论
glab mr note 123 -m "审查意见"

# 关闭 MR
glab mr close 123

# 合并 MR
glab mr merge 123
```

## 审查重点检查清单

### 安全检查
```bash
# 搜索硬编码密码
grep -rn "password.*=.*['\"]" .

# 搜索硬编码 API Key
grep -rn "api[_-]key.*=.*['\"]" .

# 搜索 TODO/FIXME
grep -rn "TODO\|FIXME" .

# 检查敏感文件
git diff --name-only | grep -E "\.env|config|secret|credential"
```

### 性能检查
```bash
# 搜索可能的 N+1 查询
grep -rn "for.*find\|forEach.*query" .

# 检查大事务
grep -rn "@Transactional" .
```

### 代码质量检查
```bash
# 查找长方法（超过 100 行）
# 需要手动检查变更文件

# 查找魔法数字
grep -rn "[^a-zA-Z0-9_][0-9]{2,}[^0-9]" .

# 查找重复代码
# 需要人工分析
```

## 审查原则

1. **保持客观**: 基于事实和最佳实践，避免主观臆断
2. **具体可行**: 不仅指出问题，更要给出具体的解决方案
3. **分清轻重**: 明确区分 Blocker、Major、Minor 问题
4. **肯定优点**: 认可做得好的地方，正向激励
5. **考虑背景**: 理解业务场景和项目约束
6. **一致标准**: 遵循项目已有的代码规范和约定

## 注意事项

- 首次使用需要配置 `glab auth login` 进行认证
- 确保有足够的权限访问目标 GitLab 项目
- 如果 MR 包含大量文件，审查可能需要较长时间
- 对于大型 MR（超过 20 个文件），建议分批次审查
- 审查意见应该建设性，帮助团队提升代码质量
